## Experiment 1 — PostgreSQL commit-order problem

### Setup

The small-plant experiment used the PostgreSQL sink with 20 machines, configured to produce 10 readings per second per machine:

```powershell
python baseline_detector.py
```

In a second terminal:

```powershell
python plant.py --sink postgres --machines 20
```

The reported database and detector counts for the run were:

| Measurement | Reported result |
|---|---:|
| Rows in `readings` for the run | 62,915 |
| Read by the detector | 51,055 |
| Not seen by the detector | 11,860 |
| Detector backlog | 0 |

The counts reconcile: 51,055 + 11,860 = 62,915. Thus, the reported missing readings were present in the database but were not processed by the polling detector.

### Why readings were missed

The baseline detector polls the table using an increasing-ID checkpoint, conceptually:

```sql
SELECT ...
FROM readings
WHERE id > last_seen_id
ORDER BY id
LIMIT 2000;
```

A PostgreSQL `BIGSERIAL` value is allocated when a row is inserted. It does not represent the order in which transactions commit. A transaction can therefore insert lower IDs and commit after another transaction containing higher IDs.

For example:

1. Gateway transaction A inserts rows with IDs 100–114 but delays its commit.
2. Gateway transaction B inserts rows with IDs 115–129 and commits first.
3. The detector polls and sees IDs 115–129, then advances its checkpoint to 129.
4. Transaction A commits IDs 100–114.
5. The detector's next query asks for IDs greater than 129, so it will not retrieve the late-committing rows.

This explains how rows can exist in PostgreSQL while the detector never sees them. Polling more frequently does not, by itself, fix this checkpoint correctness problem.

## Experiment 2 — Full-plant processing capacity

### Setup and reported observation

The full-plant configuration uses 60 machines at 10 readings per second each. The supplied run notes report 49,320 readings over 83 seconds, which is approximately 594 readings per second and is close to the configured rate of 600 readings per second.

The run notes report that detector delay and backlog increased while the plant was running. This is expected because the single detector's theoretical processing capacity is lower than the incoming reading rate.

### Capacity calculation

The model takes approximately 3 milliseconds to score one reading. Therefore, the theoretical capacity of one detector is:

\[
\frac{1}{0.003} \approx 333.33\text{ readings/second}
\]

The full plant produces:

\[
60 \times 10 = 600\text{ readings/second}
\]

The incoming rate is therefore about 266.67 readings per second higher than one detector can process. The backlog is expected to grow by approximately:

\[
600 - 333.33 = 266.67\text{ readings/second}
\]

The theoretical minimum number of detector instances at the laboratory rate is:

\[
\left\lceil\frac{600}{333.33}\right\rceil = 2
\]

At the planned rollout rate of 2,000 machines producing 50 readings per second each:

\[
2{,}000 \times 50 = 100{,}000\text{ readings/second}
\]

The theoretical minimum number of detector instances becomes:

\[
\left\lceil\frac{100{,}000}{333.33}\right\rceil = 300
\]

These are theoretical minimums based on the stated 3 ms inference time. A production deployment would require additional headroom for uneven partition loads, consumer rebalances, failures and other processing overhead.

## Stage A conclusion

The PostgreSQL baseline reveals two separate limitations:

- **Correctness:** an increasing `BIGSERIAL` ID checkpoint can skip rows when transactions commit out of ID order.
- **Throughput:** one detector processing approximately 333 readings per second cannot keep up with the 600 readings per second generated by the full laboratory plant.

These observations motivate using a partitioned event stream and parallel consumers for the higher-volume pipeline.
